# Одновременный трафик и загрузка — исправления 07.09.2026

Более поздние изменения и текущие размеры: [DELIVERY_FIXES.md](DELIVERY_FIXES.md).

Продолжение исправлений от 06.09.2026. Закрыты три дополнительных сценария, обнаруженные при проверке одновременного multicast/CLUNET трафика, и связанная ошибка конкурентного HTTP-upload.

| Сценарий | Изменение | Проверка |
|---|---|---|
| Discovery/ping приходит, когда AVR пересылает команду | Для Bridge включён `CLUNET_AUTOREPLY_IDLE_ONLY`: автоответ разрешён только при свободном передатчике. Занятая передача не заменяется служебным ответом. | Все занятые состояния и приоритеты; обычный автоответ в idle. |
| Прерывание приходит между проверкой готовности и подготовкой кадра | `clunet_try_send_fake()` атомарно резервирует буфер состоянием PREPARING. Заполнение и CRC проходят с восстановленным состоянием прерываний; короткая критическая секция завершает подготовку. UART-передача и кнопочный discovery используют этот путь. | Имитация приёма discovery непосредственно во время CRC; проверка сохранности буфера, восстановления SREG и ожидания занятой линии. |
| CLUNET постоянно заполняет очередь событий, а ESP ждёт разрешения | `service_uart()` чередует готовые события и credit-ответы. Обороты main loop во время UART TX не сбрасывают выбранную очередность. | По 1000 событий и credit-запросов одновременно, дополнительные вызовы во время занятого UART; затем отдельные потоки по 200 сообщений. |
| Два внешних загрузчика отправляют BOOT_CONTROL | Сессия закреплена за сочетанием IP + UDP-порт + CLUNET-src и единственным устройством назначения. Проверка допуска не меняет владельца; он записывается после успешного помещения кадра в очередь. | Отказы при другом IP, порте, src или dst; отклонённый пакет не продлевает срок и не переключает цель. |
| Другой узел шины входит в bootloader | Его ответ не меняет цель уже активной сессии. При отсутствии владельца START создаёт временную изоляцию только этого устройства. | START другого узла во время сессии, первый владелец после START, переход времени через UINT32_MAX. |
| Веб-интерфейс пытается начать прошивку во время внешней загрузки | `/flash/start` возвращает 409 при действующей изоляции bootloader. | Проверена ветка допуска в коде; прошивка ESP с этой веткой собрана. |
| Второй HTTP-upload приходит во время первого или активной прошивки | Проверка запроса-владельца выполняется до очистки общего firmware-буфера. Чужие части не обрабатываются, запрос получает 409; отключение владельца освобождает загрузку. | Выполняются фактические upload-callbacks с подменённым HTTP: перемежающиеся части, активная прошивка, завершение и отключение. |

## Поведение и совместимость

- Для Bridge служебный ping/discovery при занятом передатчике **пропускается**, а не откладывается. При интенсивном трафике поиск устройств может потребовать повторного запуска. Флаг включён только в конфигурации AVR Bridge; другие устройства сохраняют прежнюю политику автоответов.
- Владелец внешней загрузки закрепляется на 10 секунд бездействия; принятый BOOT_CONTROL и ответы выбранного устройства обновляют срок. Другой отправитель, адрес назначения или START другого устройства срок не продлевают.
- Внешний загрузчик должен использовать постоянные IP, UDP-порт и CLUNET-src в течение сессии. Два процесса с полностью одинаковыми этими значениями старый протокол различить не позволяет. Это изоляция в данном мосте, не аутентификация и не глобальная блокировка всех узлов физической шины.
- После появления нового владельца старая UART-очередь очищается. В очереди bootloader также применяется TTL 2 секунды. Внешний загрузчик должен сохранять протокол «команда → ответ», а не слать страницы без ожидания подтверждения.
- Raw BOOT_CONTROL через общий HTTP `/command`/`/request` больше не принимается: у этого пути нет устойчивого идентификатора отправителя. Для локальной прошивки используется `/flash`; multicast BOOT_CONTROL поддерживается с привязкой к отправителю.
- Обычные команды во время прошивки ограничиваются, SSE-события в maintenance не сохраняются для последующего воспроизведения. Физические CLUNET-устройства продолжают занимать общую линию; при перегрузке возможны потери и таймауты. Эти изменения не обещают доставку каждого пакета.

## Результаты проверки

Все проверки выполнены на реальных изменённых рабочих копиях, без загрузки в устройства:

```sh
python3 tests/concurrency_regression.py
python3 tests/stability_regression.py
python3 tests/multicast_regression.py
python3 tests/build_firmware.py --output /tmp/bridge-concurrency/build
```

Три набора тестов прошли с ASan/UBSan. В регрессионном окружении подменены аппаратные операции, UDP и HTTP, но исполняются извлечённые фактические функции драйвера, арбитра и flash-callbacks. Multicast-тест дополнительно проверяет передачу реального IP/порта в обработчик маршрутизации. Полная сборка проверяет совместимость с установленными Arduino-библиотеками. `git diff --check` изменённых компонентов прошёл.

| Сборка | Flash | Статическая RAM |
|---|---:|---:|
| AVR ATmega8, 16 MHz | 4214 байт | 794 / 1024 байт |
| ESP8266, generic 80 MHz | 401812 байт кода | 43996 / 80192 байт |

ESP IRAM вместе с зарезервированным instruction cache: 62367 / 65536 байт. Бинарники и логи: `/tmp/bridge-concurrency/build` — временный каталог. Хэши исходников: `stability-audit/concurrency-validation.json`.

Обновлять согласованную пару AVR → ESP, используя изменённые общие библиотеки. Android в этом дополнении не менялся. Испытания реальной конкуренции на шине, потерь радиоканала, bootloader и длительный нагрузочный прогон остаются необходимыми; на компьютере их результат не подтверждён.
