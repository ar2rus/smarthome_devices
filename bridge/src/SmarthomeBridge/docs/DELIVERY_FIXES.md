# Доставка и прошивка без замены bootloader — 07.09.2026

Актуальное дополнение к STABILITY_FIXES.md и CONCURRENCY_FIXES.md. Правки внесены в рабочие копии ESP SmarthomeBridge, приложения AVR Bridge, общего драйвера CLUNET и SmarthomeMonitor. В этой конфигурации Android обращается непосредственно к ESP; Java-сервер не участвует.

Исходники установленных загрузчиков `_lib/clunet/boot` и `_lib/clunet/uart_boot` не менялись: все шесть файлов сверены по SHA-256. Формат CLUNET BOOT_CONTROL, команды INIT/WRITE/DONE, ответы загрузчика и UART code=1 сохранены. Обновлять требуется приложение AVR, а не его bootloader.

## Исправления

| Проблема | Реализованное поведение |
|---|---|
| Готовность AVR не означала, что принятая команда действительно вышла на линию | UART приложения v2 передаёт номер операции и её результат: PENDING=1, TRANSMITTED=2, EXPIRED=3, REJECTED=4. На ESP дополнительно UNKNOWN=5 при отсутствии подтверждения. |
| Команда могла ждать свободной линии и выполниться значительно позже таймаута клиента | Для отправки через v2 AVR получает оставшийся бюджет, максимум 2000 мс. По истечении ожидание и дальнейшие повторы после коллизии прекращаются. Уже передаваемый кадр разрешено закончить. У старого code=1 отдельно ограничены ожидание допуска и передача — до 2000 мс каждое. |
| Потерянный ответ мог спровоцировать повтор команды | ESP повторяет запрос статуса, но не саму операцию. AVR игнорирует повтор текущего номера; после перезапуска ESP следующий номер выбирается с учётом последнего номера AVR. Это не постоянный журнал и не защита от произвольного повтора старых номеров другим отправителем. |
| Нельзя было увидеть часть потерь на AVR | `/bridge/status` показывает аппаратные ошибки UART, CRC, переполнение RX, отказы FIFO, истечение legacy-передач и минимальный наблюдавшийся запас стека. ESP отдельно считает подавленные события и события без подписчиков. |
| Дубли INIT, несколько WRITE одновременно и некорректные страницы могли повредить загрузку | Для внешнего multicast-загрузчика добавлен автомат INIT → READY → WRITE → WRITTEN с одним неподтверждённым блоком, проверкой длины, номера страницы и её границ. Ошибка передачи останавливает этот поток. Идентичный INIT повторно не посылается. |
| Ошибочный HEX или адрес могли попасть в загрузку | Проверяются checksum, EOF, адресные записи, переполнение адреса, конфликтующие перекрытия и наличие reset vector. Нечётная длина дополняется FF. Параметры адреса, границы приложения и таймаутов строго числовые; некорректный адрес больше не превращается в 0. |
| Последний блок и DONE считались достаточными для успеха | Для удалённой цели ожидается результат передачи DONE, затем ответ приложения на PING с проверочным значением. Для AVR самого моста — BOOT_COMPLETED и свежий ответ приложения UART v2. Через 6 секунд без подтверждения результат `unconfirmed`. |
| Служебные UART-запросы могли попасть в прежний UART bootloader | Пока известная сессия AVR-0 находится в bootloader, запросы v2 отключены; загрузка использует прежний code=1. Во время ожидания старта приложения AVR-0 PING не посылается. |
| Последовательность SSE не обнаруживала потерь до ESP | SERVICE включает счётчики потерь AVR; их изменение инициирует перечитывание состояния Android, даже без разрыва seq. |
| Android мог обработать задержанное нажатие как свежее | DATA содержит uptime отправки и возраст очереди. Клиент использует монотонное время, отбрасывает события старше 2 секунд и запрашивает состояние. Учтены переполнение 32-битного uptime и перезапуск ESP. Задержанный heartbeat не переводит часы назад. |
| Опрос экранов продолжался в maintenance | Два административных экрана показывают прошивку и откладывают refresh. После снятия maintenance клиент запрашивает синхронизацию состояния. |

## Совместимость и точные границы гарантий

UART приложения v2: code=3 `{nonce}`; code=4 — 18 байт `{nonce, version=2, ready, lastIdLE16, result, uartErrorsLE16, fifoDropsLE16, rxOverflowsLE16, legacyExpiredLE16, crcErrorsLE16, stackMinFreeLE16}`. Code=5 — `{idLE16, remainingMsLE16, прежний CLUNET-пакет}`; code=7 — отмена `{idLE16}`. Физический CLUNET-кадр и формат прошивки устройств не расширены.

TRANSMITTED подтверждает завершение отправки кадра на CLUNET, но не исполнение команды адресатом. HTTP `/command` по-прежнему подтверждает принятие в очередь. При потере результата ESP возвращается к работе с UNKNOWN после бюджета + 1 с; повтор команды не выполняется. Следующая отправка требует свежего ready от AVR. Отмена также ограничена доставкой UART; основной механизм прекращения — дедлайн на AVR.

`applicationResponded=true` означает только ответ приложения. `imageVerified` всегда false: старый загрузчик не предоставляет чтение/CRC flash или идентификатор установленного образа. `imageCrc32` — CRC загруженного файла в памяти ESP, не проверка устройства. Даже старое приложение после неудачной попытки может ответить на PING.

Локальная загрузка по умолчанию ограничена 7168 байтами приложения (ATmega8, boot начинается с 0x1C00). Для AVR-0 эту границу нельзя увеличить. Для других адресов есть параметр `limit`, максимум 8192 в пределах существующего буфера; его нужно сверить с реальной разметкой устройства. READY сообщает размер страницы, но не начало bootloader. Внешняя multicast-загрузка ограничена 7168 байтами. При READY также проверяются допустимый размер страницы и диапазон номеров 0–127, поскольку старый загрузчик хранит номер в signed char.

В старом WRITE/WRITTEN нет номера блока или сессии. Дубликат/задержавшийся ACK при неудачном совпадении фаз нельзя полностью отличить от нового. Для страницы больше 64 байт повтор уже подтверждённого первого фрагмента может выглядеть как следующий такой же фрагмент. Автомат ограничивает допустимые переходы, но не создаёт отсутствующую в протоколе идентичность блока. Автоматический повтор WRITE не добавлен.

Lease защищает только трафик, проходящий через этот ESP. Другой физический узел или другой мост может передавать на общую CLUNET. Коллизии, перегрузка, пропажа питания, ошибки электрических уровней и UDP по-прежнему могут приводить к потерям. При сбое прошивки нельзя гарантировать сохранность приложения на старом загрузчике. Если ESP перезапустился посреди UART-загрузки и не получил START, он не располагает сохранённым состоянием сессии.

SSE не стал долговременным журналом. Разовые потерянные нажатия не восстанавливаются; состояние восстанавливается там, где подписчик реализует повторный запрос. Возраст события оценён относительно принятого RESET/uptime: общая задержка первоначальной синхронизации неизвестна. Точное сквозное время от физического события AVR пока не передаётся. При старом сервере без uptime остаётся прежняя обработка событий.

## Проверка

Все команды выполнены после применения файлов в реальные рабочие копии:

```sh
python3 tests/stability_regression.py
python3 tests/multicast_regression.py
python3 tests/concurrency_regression.py
python3 tests/delivery_regression.py
python3 tests/android_client_regression.py
python3 tests/build_firmware.py --output /tmp/bridge-delivery/final-build
```

Пять наборов тестов прошли. C/C++ проверки используют ASan и UBSan; исполняют фактические функции с имитацией аппаратуры/HTTP/UDP. Новый delivery-тест проверяет ISR и отмену/дедлайн, отсутствие повторной отправки, потерянные ответы, переполнение времени, HEX, автомат внешней загрузки, прежние байты UART DONE и различие статусов окончания. Android host-тест проверяет реальные классы клиентов с подменёнными Android/OkHttp/OkSse; это не APK и не проверка Activity на устройстве. Использован локальный Jackson 2.14.1; проектная версия 2.8.5 отдельно не собрана.

| Сборка | Код / flash | Статическая RAM |
|---|---:|---:|
| AVR ATmega8, 16 MHz | 5180 байт; приложение помещается до 0x1C00 | 820 / 1024 байт |
| ESP8266 Core 3.1.2, generic 80 MHz, 4M1M, lwIP hb2f | 407280 байт | 46392 / 80192 байт |

ESP IRAM с instruction cache: 62367 / 65536 байт. После статических данных AVR остаётся 204 байта на стек; `avrStackMinFree` оценивает наблюдавшийся запас по заполнителю, не доказывает отсутствие переполнения. Сборки проходят с предупреждениями, включая прежний устаревший API ArduinoJson и signedness в ClunetMulticast. `git diff --check` изменённых компонентов прошёл. Хэши исходников, проверки загрузчиков и размеры сохранены в `stability-audit/delivery-validation.json`. Логи и бинарники находятся во временном `/tmp/bridge-delivery/final-build`.

## Ввод в работу

1. Обновить **приложение** AVR Bridge, затем ESP согласованной версии. Bootloader и его fuse/раздел не перепрошивать. Новый ESP не передаёт обычные команды через старое приложение AVR v1. В ESP нужны изменённая библиотека ClunetMulticast и веб-файлы, включая flash.html.
2. Собрать и установить SmarthomeMonitor после восстановления Android SDK/проектных зависимостей. В текущем окружении полная APK-сборка не выполнена.
3. Проверить `/bridge/status`: `avrProtocol=2`, свежий `avrProtocolReady`, рост `txTransmitted`, отсутствие необъяснимого роста ошибок/UNKNOWN. Проверять `avrStackMinFree` под нагрузкой. До первого UART-ответа его значение не является измерением.
4. На доступном тестовом устройстве совместить команды HTTP, multicast и поток событий CLUNET; затем проверить изоляцию загрузки и возврат приложения. Отдельно испытать занятость линии, потерю UART-ответа, двух загрузчиков, Wi-Fi reconnect и замедление SSE-клиента. Не начинать испытания с недоступных для восстановления устройств.
5. Провести 24–72 часа реальной работы с сохранением диагностик. Программные регрессии и сборки выполнены; аппаратное испытание, прошивка устройств и долговременный прогон здесь не проводились.
